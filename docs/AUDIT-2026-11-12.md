## Resumen

No se ha encontrado una ejecución remota trivial ni secretos versionados. Las barreras principales de Electron están razonablemente aplicadas: `contextIsolation`, `sandbox`, `nodeIntegration: false`, navegación bloqueada, permisos denegados, CSP estricta, allowlist de red y validación Zod de IPC.

El riesgo más importante no es de seguridad clásica: es de **primera instalación**. Imago sigue exigiendo un entorno Python externo para EmbeddingGemma y no tiene un onboarding que instale o verifique ese entorno antes de ofrecer descargas de modelos. Un usuario puede descargar más de un GB de pesos y descubrir después que la indexación no puede arrancar.

## Hallazgos

### A1 — P0 — La primera instalación de IA no es autosuficiente

- El valor por defecto es `python3` en macOS/Linux y `python` en Windows: `electron/db/repository.ts:867`.
- La UI de Modelos locales reconoce que EmbeddingGemma requiere el entorno Python del README: `src/components/Settings.tsx:305-314`.
- No hay detección al arrancar, asistente de instalación de dependencias, ni comprobación previa antes de permitir la descarga de EmbeddingGemma.
- El modelo de embeddings se puede descargar y verificar sin que el runtime Python esté disponible. El fallo aparece más tarde, al indexar, con un error de `spawn`/runtime crudo.
- No hay un grafo de dependencias que instale automáticamente runtime + modelo + pesos, ni un preflight de espacio en disco.

**Impacto:** bloquea la experiencia de un usuario nuevo y contradice el modelo de Nodus, donde el motor principal funciona sin Python.

**Recomendación:** migrar EmbeddingGemma a ONNX/Transformers.js, descargar modelos y llama.cpp bajo demanda y crear un onboarding con comprobación de disco, licencia, progreso, reanudación y estado final. No es solo un cambio de documentación.

### A2 — P1 — Un modelo corrupto con el tamaño oficial no se podía reparar

- `Models.verify()` detectaba el hash incorrecto y lanzaba el error, pero dejaba el archivo en disco: `electron/ai/models.ts:75-101`.
- `Models.downloadFile()` se saltaba la descarga si el archivo existía y medía lo mismo: `electron/ai/models.ts:131-136`.
- Consecuencia: “Descargar” de nuevo no reparaba el modelo; el mismo archivo corrupto se reutilizaba y la verificación fallaba siempre.

**PoC:** se creó un modelo ficticio de 3 bytes con tamaño oficial y contenido incorrecto; `verify()` falló y el archivo seguía presente. Tras la corrección, `verify()` elimina únicamente el archivo que no supera la comprobación, de modo que una nueva descarga puede recuperarlo.

**Estado:** corregido en esta auditoría con regresión en `tests/integrity.test.ts`.

### A3 — P1 — La actualización del runtime no es atómica

- `Models.prepareRuntime()` borra el directorio `bin` existente antes de extraer el runtime nuevo: `electron/ai/models.ts:215-221`.
- Si la extracción falla, el usuario se queda sin runtime previo y sin runtime nuevo.
- La descarga y el SHA-256 sí se verifican antes; el problema es el reemplazo local, no la autenticidad de la descarga.

**Recomendación:** extraer en un directorio staging, verificar el ejecutable, y sustituir el `bin` anterior solo al final; conservar el anterior hasta que el nuevo esté listo.

### A4 — P1 — `.gitignore` no cubría credenciales, pesos, backups ni instaladores

El `.gitignore` inicial ignoraba dependencias, `release`, `.venv`, SQLite y test-results, pero no cubría:

- claves y certificados (`*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.mobileprovision`, etc.);
- pesos y modelos (`*.gguf`, `*.onnx`, `*.safetensors`, `*.pth`, `models/`, etc.);
- backups de usuario (`*.imago`);
- instaladores generados fuera de `release/` (`*.dmg`, `*.AppImage`, `*.deb`, `*.rpm`, `*.exe`, `*.msi`, `*.blockmap`);
- estado local de agentes (`.codex/`).

**Estado:** corregido en esta auditoría. El árbol versionado actual no contenía secretos, certificados, pesos ni instaladores.

### A5 — P2 — Restaurar puede dejar originales huérfanos si falla la transacción

`restoreBackup()` mueve los originales verificados a `originals/` antes de ejecutar la transacción que sustituye las tablas: `electron/export/backup.ts:182-192`. Si la inserción posterior falla, la base de datos se conserva por el rollback, pero los archivos nuevos permanecen.

**Impacto:** no se pierde la colección destino, pero quedan archivos huérfanos y el siguiente intento puede encontrar un original existente. Debe limpiarse o registrarse el staging para una recuperación controlada.

### A6 — P2 — Los ZIP de copia/Notion permiten hasta 32 GB descomprimidos

`Archive.open()` limita a 32 GB y 100.000 entradas (`electron/import/archive.ts`), pero no comprueba el espacio libre antes de extraer. Un ZIP elegido por el usuario puede llenar el disco.

**Recomendación:** preflight de espacio, límite de expansión y extracción con cuota; no es una ejecución remota, pero es una vía de denegación de servicio local.

### A7 — P2 — Endpoints personalizados pueden recibir una clave almacenada

`providerBase()` permite HTTPS arbitrario y HTTP solo loopback (`shared/aiConfig.ts:30-49`), y `ApiProviders` adjunta la clave guardada a ese endpoint. Esto es intencionado para proveedores personalizados, pero un renderer comprometido podría cambiar el endpoint y solicitar una tarea para enviar la clave a otro HTTPS.

Las barreras actuales (`contextIsolation`, `sandbox`, CSP, sin HTML crudo) reducen mucho la probabilidad. Como defensa adicional, conviene confirmar endpoints personalizados o exigir una acción explícita antes de usarlos con claves existentes.

### A8 — P2 — Los enlaces Markdown externos no se abren

`MarkdownView` renderiza enlaces externos con `target="_blank"`, pero la ventana deniega `window.open` y `will-navigate`. No es un riesgo de seguridad, pero el usuario ve un enlace que no hace nada. Debe abrirse mediante `shell.openExternal` con allowlist HTTPS, o mostrarse como texto no interactivo.

### A9 — P2 — No hay CI de release para las cinco plataformas

El árbol actual tiene CI para macOS ARM64, macOS Intel, Windows x64 y Linux x64, pero no Linux ARM64. Los instaladores Windows/Linux actuales no están construidos con el árbol final. Por tanto, la primera instalación y la matriz de release no están verificadas en GitHub.

### A10 — P2 — Firma/notarización aplazada

Los artefactos son unsigned/ad-hoc. No es un bloqueo inmediato por decisión del usuario, pero sí un requisito antes de una release pública.

## Controles que sí han resistido la revisión

- Renderer con `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, `webSecurity: true`: `electron/main.ts:441-450`.
- Navegación y `window.open` bloqueados; permisos denegados.
- CSP sin scripts inline; imágenes limitadas a `self`, `imago:`, `data:`, `blob:` y tiles de OSM.
- IPC comprobando `event.sender`, `senderFrame` y validación Zod estricta.
- Protocolo `imago://asset` limitado a dos segmentos y patrón de ID.
- Descargas de modelos limitadas a HTTPS y hosts conocidos, con SHA-256 y tamaño.
- Archivos ZIP/tar con rechazo de rutas absolutas, `..`, symlinks fuera del destino y límites de tamaño.
- Secretos cifrados con `safeStorage`; sin fallback a texto plano; permisos 0700/0600.
- Copias con `integrity_check`, `foreign_key_check`, `trusted_schema=OFF` y rollback transaccional.
- `npm audit` y `npm audit --omit=dev`: 0 avisos.
- Sin secretos, certificados, pesos ni instaladores en los archivos versionados; el árbol tiene 164 archivos y el mayor es el gazetteer legal de ~916 KB.

## Primera instalación: recorrido auditado

Lo que funciona desde un perfil limpio:

- Crear bases, importar CSV/imágenes, búsqueda literal y edición.
- La app no exige modelos para las funciones básicas.
- Los modelos se organizan por tarea y muestran licencia, revisión y estado.
- Las descargas tienen progreso, pausa/reanudación y SHA-256.

Lo que no está resuelto:

- Python externo para EmbeddingGemma.
- Descarga de un modelo que después no puede ejecutarse por falta de entorno.
- Ausencia de un asistente único “preparar búsqueda semántica”.
- Dependencia entre LFM3 y llama.cpp no instalada automáticamente.
- Falta de preflight de disco y de un estado de instalación global.
- Falta de una prueba E2E desde un perfil limpio que recorra descarga → verificación → indexación → búsqueda → cierre y reapertura.

## Recomendación de orden para Codex

1. Migrar a ONNX/Transformers.js + llama.cpp descargable y eliminar Python del flujo principal.
2. Implementar el gestor de modelos como grafo de dependencias, con preflight de disco, staging atómico, verificación y recuperación de corrupción.
3. Añadir onboarding de primera instalación y un E2E limpio.
4. Añadir Linux ARM64 a CI y construir/probar las cinco plataformas.
5. Resolver los P2 restantes y aplazar firma/API/CUDA/corpus hasta que el usuario pida release.
